# Sloth Lee Mail — full audit, 18 Nov 2026

Scope: the mail service end to end — the edge and DNS, the server, the web client, the
watchdogs, and the backup. Method: every claim below was measured against the live
deployment (`https://mail.slothlee.xyz`) or read out of the running host, not inferred
from source. Where something was only checked statically it says so.

## Health summary

| Area | Result |
|---|---|
| Edge hardening | Strong. CSP, HSTS preload, `frame-ancestors 'none'`, no-referrer, permissions policy, TLS client cert required at origin |
| Mail authentication | Strong. SPF `mx -all`, DMARC `p=reject` strict, DKIM, MX + DANE pin matching the served cert, MTA-STS, TLS-RPT, DNSSEC with DS at the registry |
| Web client | Renders and works; 267 unit tests, 0 failing contrast pairs in both themes, 0 controls under 44 px at 390 px |
| API | 13/15 live checks pass; the two "failures" are the server correctly refusing an unencrypted payload |
| Off-site backup | **Broken since 17 Nov** — no off-site copy for two days |
| Monitoring | **Half dead** — the app-render probe was absent for 44 hours; one watchdog crying wolf hourly |

## P0 — fix now

**1. A password change permanently destroys mail older than 200 messages.** See P0-C below:
the client treats page one of a paginated endpoint as the whole mailbox, re-encrypts only
those, reports success, and discards the old key. This outranks everything else in this
document — it is silent, irreversible, and fires on a normal user action.

**2. Export truncates at 200 and says it wrote everything** (P0-D) — same cause.

**3. Off-site backups have not left the host since 16 Nov.**
`/usr/local/bin/mail-offsite-backup.sh` uploads a ~38 MB encrypted archive to a private
GitHub repo through the contents API. Since 17 Nov every run fails:

```
ERROR upload failed: "Sorry, the file is too large to be processed."
```

The archive grew past what that API accepts once base64-encoded (~54 MB). Last good
upload: `slothmail-20261116-041001.tgz.gpg`, 40,051,591 bytes. The job exits 1, so the
cron alert fires — but the alert has now fired twice and nothing changed, and the probe
that would have escalated it was itself dead. The monthly restore drill still passes,
which is exactly the trap: a drill against a *local* archive proves the archive is good
and says nothing about whether a copy exists off the box.

Fix options: (a) split the archive into <40 MB parts and upload each, keeping the same
repo and zero spend; (b) move to object storage (B2/S3) with lifecycle rules. (a) needs
no decision and no money, so it is the default.

## P1 — fix this week

**2. The app-render probe was dead for 44 hours.** Heartbeat
`/opt/sloth-bot/status/app-probe.heartbeat` last moved 2026-11-16T13:26Z. There was no
cron entry on the Hermes host at all — no crontab, no timer. The mail host's own watchdog
caught it and mailed hourly, which is how the hole was found, but nobody was acting on it.

*Fixed during this audit:* `/data/scripts/mail-app-probe.cjs` renders the live app as a
signed-in phone user, asserts the inbox and the compose control, refreshes an expired token
before judging, and stamps the heartbeat the watchdog reads. Registered as Hermes cron
`ec78d3200f34` every 30 minutes, silent when healthy. Verified: probe ran, heartbeat age 2 s.

**3. The DNS watcher cried wolf every 30 minutes for four days.** It asserted the MTA-STS
policy id was `2026111201`; the policy was legitimately republished as `2026111401` on
14 Nov, so the check failed forever while every real invariant passed. *Fixed during this
audit:* expectation updated, verified by hand that all eleven other checks pass. The design
flaw remains — a hardcoded id means every legitimate policy bump becomes an alarm; the
watcher should read the id from the published policy file.

## P2 — next

**4. No CAA record** on `slothlee.xyz`. Any CA can issue for the domain. Adding
`0 issue "pki.goog"` (Cloudflare's CA) and `0 issuewild` closes it.

**5. Search is client-side.** There is no `/email/search` route on the server; the client
searches what it has fetched (`/email/list` then `/email/bulk`). Fine at 15 accounts and a
few hundred messages; it will silently miss older mail as mailboxes grow, and it costs a
full download per session.

**6. One 306 KB JavaScript chunk.** Total first load is 333 KB compressed, which is why
first paint is 164 ms — but everything ships in `index-*.js`: composer, settings, admin,
PGP. Splitting admin and settings off the initial chunk would cut the critical path by
roughly half for the people who never open them.

**7. A watchdog that cannot be trusted is worse than none.** Two of the three watchdogs
were misreporting (one dead, one false). The estate probe was healthy throughout. The
lesson worth encoding: every watchdog must be tested by breaking the thing it watches.

## Phase 1 — the watchdogs, broken on purpose

A watchdog you have never seen fire is a hypothesis. Each one was given a fault it
should catch, and the test was the alert arriving — not the script exiting.

| Watchdog | Fault injected | Result |
|---|---|---|
| App probe (`ec78d3200f34`, 30 min) | pointed at a dead URL | exit 1, `APP PROBE FAILED: blank or missing UI`, heartbeat `… 1`; a normal run afterwards restored verdict `0` |
| DNS / DANE watcher | one expectation corrupted in a copy of the script | `ALERT 1 problem(s)` in the log **and** Postfix accepted the mail: `to=<tibs@slothlee.xyz> … status=sent (250 2.0.0 OK)` |
| Off-site backup | token file replaced with a bad one | exit 1, `401` logged, so the cron's `|| mail-alert.sh` fires — the upload failure can no longer exit quietly |
| Estate probe (Hermes cron) | bogus health URL + surface | `⚠️ health endpoint answered HTTP 404` — the alert text is produced |
| Container/disk watcher | `SLOTH_DISK_THRESHOLD=1` | alert raised, mail sent `rc=0` |

**The break-test found a real hole: the Discord DM channel is dead.** Every alert attempt
returns `401 Unauthorized` from `discord.com/api/v10`, so container, disk and probe alerts
reach you by **email only**. Worse, the watchdog sent the mail *before* attempting the DM and
logged the failure only to its own log file — a dead second channel looked like success.

Fixed while testing: the DM is attempted first, its failure is logged as
`delivery degraded — DM failed (http 401)`, and the mail now carries a line naming the
channel that did not deliver. Verified on a forced disk alert: DM 401 → degraded log line →
mail sent with the note. The 401 itself needs a fresh Discord token (that is a secret only
you can supply); until then email is the honest channel and the alert says so.


## Phase 2, first item — remote content blocked (done)

Opening an HTML message used to fetch the sender's images immediately: this morning a
single 1×1 pixel in a message caused `GET /__track/open-1x1.gif` with the reader's IP and
user agent. That is a read receipt, and it is the one privacy leak that survives otherwise
sound encryption.

`prepareMail` now neutralises remote `img`/`srcset`/`background`/CSS `url()`: the source is
replaced with a transparent pixel, the original is kept in `data-sloth-remote-*`, and the
reader is told *"1 remote image was blocked, so the sender cannot tell you opened this"*
with a **Show images** button. `data:` and inline images are untouched — they cannot call
out. The frame also lost `allow-popups-to-escape-sandbox`.

**Verified on production (`eee3c69`) with the same pixel that leaked this morning:**

| action | requests to the tracker |
|---|---|
| open the message | **0** (was 1) |
| click "Show images" | **1** — the sender's image loads on request, once |

Seven tests pin it, including that the stashed URL survives and that a CSS `url()`
background is caught as well as an `<img>`. Suite 277.


## Phase 2, second item — the KT signer is pinned (done)

`verifyHeadSignature` used to verify against `head.pk` — the key travelling in the same
response as the head it vouched for. A server could mint a keypair, sign its own head, and
every check passed. The send-time "provable key" refusal therefore only stopped a server
*changing its mind later*; it could not stop a substituted directory.

The ML-DSA-65 key now ships as a build constant (`src/ktPinnedKey.js`), compared as **decoded
bytes** so padding or a re-encode cannot pass for a different key. The check runs first in
`verifyProof`, before any tree math — there is no point computing roots for a signer this
build does not trust — and an untrusted signer returns its own reason, `kt_signer_unpinned`,
with a sentence that says what it means: *"The server is presenting a key directory signed by
a key this build does not trust. Nothing was sent."*

**Verified on production (`3823ec9`):** a full encrypted round trip (compose → send →
receive → decrypt in the reader) still succeeds, which is the proof the pin matches the live
signer. 283 tests, 6 new, including that a well-formed foreign key is refused and that
re-encoded base64 of the *pinned* key still passes.

**The trade this makes, stated plainly:** if the server ever rotates its KT signing key,
sending refuses until a build carrying the new key ships. That is the point — fail closed —
and it is written into the file so rotation is a deliberate act with two keys listed during
a rollover, not a silent surprise.


## Phase 2, third item — the lock, and the limit of what it can claim

The lock was read from an `OpenNeutron-E2EE` header inside the parsed body, so a hostile
server could send plaintext, set the header, and the reader showed a padlock. It is now
derived from whether the message arrived with a `message_key` this browser decrypted — a
fact the client establishes itself.

**Adversarial test on production (`b72746c`):** a plaintext message posted with
`OpenNeutron-E2EE: true` was opened — the lock still appeared. Investigating that rather than
declaring victory found the reason, and it is more interesting than the bug: **the server
seals inbound mail to the recipient itself.** A plaintext message to `qa@slothlee.xyz` arrives
with a `message_key` and a ciphertext body (`message_key present: True`). So "this arrived
encrypted" describes the server's storage, not the sender's intent, and no header-level fix
can make the lock a statement about who sent it.

Only a sender signature can. That is designed in **`docs/MESSAGE-AUTHENTICITY.md`**: an
ML-DSA-65 signing key per identity published in the KT leaf, an `SLW2` envelope whose
signature covers the ciphertext (not the plaintext, so it verifies before decryption) plus
the recipient-set hash and sender address, three honest reader states — *Verified sender*,
*Sealed, sender unverified*, *Not encrypted* — and a hard refusal that withholds the body on
a signature mismatch. The server change is one field on the KT leaf; the client half is
pointless before it.

## Code audit 2 of 3 — security and cryptography

Scope: `src/` crypto, auth, rendering and storage paths, read-only. 15 findings: 6 P1, 9 P2,
no P0, and no hardcoded secrets or `dangerouslySetInnerHTML` anywhere. Three of the six P1s
were re-tested here; each is marked with its verification.

**P1-1 · Key transparency verifies a key the server supplied (VERIFIED, code).**
`kt.js:255` — `verifyHeadSignature(head)` takes `pk` from `head.pk`, the same object as the
signature, and verifies against it. Nothing pins that key to a build constant. The head
pinning that exists is TOFU and therefore binds a browser to whatever it saw *first*; it
stops regression and forking for a returning browser, but a freshly-signed-in client, or a
server that mints its own key, produces a self-consistent proof that passes every check.
So the send-time "provable key" refusal cannot stop key substitution — it only stops the
server changing its mind later. Fix: ship the KT signing key as a build constant, fail
closed if `head.pk` differs.

**P1-2 · Remote content loads on open (VERIFIED, live).** Sent an HTML mail containing one
1×1 image and opened it at 1440. The browser issued
`GET /__track/open-1x1.gif` and the edge logged it with the reader's IP and user agent. No
"load images" gate, no proxy, no `cid:` resolution. Every HTML message is a read receipt,
and an E2EE mailbox leaks the reader's IP to the sender — the exact thing encryption is
supposed to prevent. Fix: block remote `img`/`background`/`srcset` in `prepareMail`, expose
a per-message "Load images", proxy through the mail host, resolve `cid:` locally.

**P1-3 · No message signatures; the lock is a body header (VERIFIED, code).**
With no `message_key` the body is treated as plaintext and rendered if it looks like a
message (`crypto.js:495`), and the "end-to-end encrypted" indicator is read from an
`OpenNeutron-E2EE` header *inside the parsed body* (`emailParser.js:355`). A hostile server
can strip the key, substitute any mail, and set that header to display a lock.
Confidentiality still holds — the server cannot read the mailbox — but integrity and the
meaning of the lock do not. Fix: sign sealed payloads with the sender's KT-verified key and
derive the lock from the verified signature only.

**P1-4 · One global bcrypt salt (VERIFIED independently).** `hashPassword` is bcrypt cost 10
over the constant `OpenNeutronAuth1` for every user on every install, and that output *is*
the wire credential. Building the QA mailbox required exactly this hash, which is how it was
confirmed. One precomputed table covers every account; a leaked hash is a login. Fix:
per-user server-issued salt; move to Argon2id; bind the credential to a server challenge.

**P1-5 · The private key sits in `sessionStorage` as plaintext base64 (VERIFIED by the
harness).** Seeding `openneutron.private_key` is how automation reads mail, which is the
same door any same-origin script or extension has. Keys are generated `extractable: true`.
It bypasses the whole "the password unwraps the key" model. Fix: memory-only where possible,
otherwise keep the wrapped blob and re-prompt via the existing `UnlockModal`.

**P1-6 · Header injection on reply (NOT YET VERIFIED).** `encodeRfc2047Word` returns ASCII
unchanged and header values are concatenated without CRLF stripping
(`emailBuilder.js:16-30`), while `decodeRfc2047` can produce real `
` from a subject the
sender controls; reply pre-fills subject from it. Dataflow is real and matches CWE-93, but I
have not reproduced it end to end, so it is recorded as unverified until it is.

**P2s worth naming:** `Math.random()` fallback for the AES key (`crypto.js:305`) — fail-open
in the one place that must fail closed; sign-out never revokes the token server-side while a
30 s poll keeps replaying it; subjects posted in clear to `/note/create` and
`/email/sendencrypted` (a real gap against "zero-knowledge" wording); `transformResponse`
regex-patches JSON strings and silently corrupts bodies containing 16-digit numbers;
drafts held unencrypted in `localStorage`; ~20 `console.log`s including a storage dump on
logout; `allow-popups-to-escape-sandbox` on the mail frame; sender favicons fetched from
`google.com`, disclosing every correspondent's domain to Google.

**Verified sound (do not re-litigate):** DOMPurify with scripts/styles/forms forbidden, into
a blob iframe with **no `allow-scripts`** — a sanitizer miss cannot execute; forced
`rel="noopener noreferrer"`; AES-256-GCM with fresh IVs and versioned envelopes; RSA-OAEP-4096
with matched MGF1; hybrid ML-KEM-768 with transcript binding; KT hashing and
consistency-proof math correct and test-pinned; the password never leaves the client; PGP
private keys always passphrase-wrapped; PQ secret wrapped before upload.

**The honest one-line verdict:** confidentiality of the ciphertext is sound and the
rendering boundary is sound. What is *not* sound is the trust story around it — the KT proof
is self-signed, the lock can be faked by a stripped header, and opening mail leaks the reader
to the sender. Those three are the difference between "encrypted" and "trustworthy".

## Code audit 3 of 3 — client ⇄ server contract

Scope: ~70 client calls against the server's route table and handler DTOs, read-only. No
dead routes, no method mismatches: `sendencrypted`, KT, trash, snooze, group, alias, mailbox,
push and admin payloads all line up field for field. **Two P0s, both from one misuse of a
paginated endpoint.**

**P0-C · Changing your password destroys mail older than the first page (VERIFIED in code).**
`/api/email/list` is paginated — `DEFAULT_PAGE = 200` (`email.rs:116,267`) — and says so in
its own comment. The client's `emailListAll()` (`api.js:201`) posts a **null body**, so the
server returns page one, and the client treats that as every uid in the mailbox.
`ChangePasswordModal` then loops that list, re-encrypts each message to the new key
(`ChangePasswordModal.jsx:126-148`), reports "All N emails re-encrypted successfully", and
discards the old private key. Mail beyond the 200th is still sealed to a key that no longer
exists **in any client** — permanently unreadable, and the UI said it succeeded.

This is the single most dangerous bug in the audit. Any mailbox over 200 messages that
changes its password loses the remainder, silently, with a success message.

**P0-D · Export silently truncates at 200 (VERIFIED in code).** Same root cause:
`ExportSection` (`ExportSection.jsx:37-42,86-95`) exports what `emailListAll()` returned and
reports "Wrote N messages". Sent mail is never included at all. A person who exports before
deleting an account gets a partial archive they believe is complete.

Fix for both: make `emailListAll()` loop `offset` until a short page comes back (and fail
loudly if any page errors), surface `total`/`has_more`, and — for password change
specifically — verify by attempting to decrypt every message before swapping keys, refusing
to finish if any cannot be read. An irreversible migration must prove itself before it
destroys the old key.

**Also found:** `/admin/users/suspend` is registered `Authenticated` rather than `Admin`
(`main.rs:610`) — the handler still calls `require_admin`, so it is safe today, but the
router-level guarantee that every other admin route has is missing; one refactor away from
being a hole. And 11 P1 robustness gaps: a failed inbox fetch is swallowed to an empty
inbox (`useEmailFetch.js:106`); a KT `409 not_current` race is shown as "the key directory is
gone, nothing was sent"; Sent is capped at 200 with no "load older"; every 401 fires an extra
`/user/me`; `/email/publickeys` runs on each keystroke of the recipient list; trash renders
empty on any 500; the Login page's `/signup` link leads to NotFound although the server has
